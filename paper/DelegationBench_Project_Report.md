# DelegationBench 项目实验总结

日期：2026 年 8 月 13 日

## 1. 我想研究的问题

这个项目关注一个很具体的问题：agent 在执行任务的过程中，如果突然从环境里看到一条新的信息或指令，它接下来的行为会不会被带偏？如果会，我们能不能把这种变化和 agent 本身正常的随机性区分开？

这件事比一开始想象的难。即使给 agent 完全相同的任务，它两次执行时也可能先打开不同文件、采用不同工具顺序，或者走不同但都合理的路径。因此，单纯看到两条轨迹不同，并不能说明新增信息产生了影响。

为了解决这个问题，我构建了 DelegationBench。每个任务都生成一组 control 和 treatment 轨迹：两边从同一个任务和环境开始，只有 treatment 会在执行到一定步骤后看到额外信息。这样可以分别比较暴露前和暴露后的差异，而不是把所有差异都归因于干预。

## 2. 最主要的结果

DelegationBench v1 一共包含 160 组配对任务、320 条真实轨迹。其中 133 组真正执行到了预定的暴露位置，可以用于前后比较。

最核心的结果是：暴露后，两条轨迹之间的行为差异明显增大。action divergence 从暴露前的 0.2199 上升到暴露后的 0.7186，平均增量为 **0.4986**，95% 置信区间为 **[0.4400, 0.5565]**。以 capability sequence 计算时也得到相同方向的结果，平均增量为 **0.3157**，95% 置信区间为 **[0.2716, 0.3623]**。

Coding 和 Web 任务中都能看到这一现象，但幅度不同：

| 任务类型 | 可用配对数 | 平均增量 | 95% CI |
|---|---:|---:|---:|
| Coding | 80 | 0.3281 | [0.2607, 0.3921] |
| Web | 53 | 0.7561 | [0.6875, 0.8192] |

Web 的变化更大，二者差值为 0.4281，95% 置信区间为 [0.3322, 0.5196]。这个结果说明，不同任务环境对新增信息的响应程度可能不同。不过，它不能直接解释为 Web agent 更不安全，因为这里测量的是轨迹变化，不是安全后果。

## 3. 一个意外但重要的发现

在 133 组可用配对中，有 60 组在新增信息出现之前就已经走上了不同路径，占 **45.1%**。这说明 agent 的正常执行过程本身就有很强的随机性。

我进一步把数据分成两类：暴露前完全一致的轨迹，以及暴露前已经分叉的轨迹。前一类的平均增量是 0.6999，后一类是 0.2538；两类的置信区间都在 0 以上。也就是说，即使 agent 原本已经因为正常随机性走了不同路线，新增信息出现后仍然能观察到额外变化。

我认为这是项目中很重要的一点：监控 agent 时，不能把“和另一条轨迹不一样”直接当成异常。更合理的做法是先估计正常路径变化，再看暴露后是否出现额外偏移。

## 4. PIDR 做到了什么

在完成 benchmark 之后，我尝试设计 PIDR，希望表示能够少受 Coding/Web 这类任务范式差异影响，同时保留与干预有关的变化。

在冻结的 seed-4 测试中，RAW 表示的 post-exposure separation 是 0.2979，PIDR-v1 是 0.6411。PIDR 相对 RAW 的增量为 **0.3900**，95% 置信区间为 **[0.2851, 0.5020]**。在后续已经打开的数据上，PIDR 的表示分离也高于 CORAL 和 MMD。

不过，这个结果目前只能说明 PIDR 在“表示空间里把干预后的轨迹拉开”这件事上做得更明显，还不能说明它是更好的实际监控器。PIDR 的 AUROC 提升没有得到统计确认，pair detection 没有超过 RAW，而且出现了 3.13% 的 benign false alarm。

所以我目前对 PIDR 的定位是：它是一个有希望的表示方法原型，而不是已经可部署的检测器。

## 5. 哪些尝试没有走通

项目中也有几条路线没有得到预期结果。

第一，早期的跨任务监控器泛化很差。Coding 训练、Web 测试时，NDTR 的 AUROC 只有 0.4416，而且把全部 control 都报成了异常；CDM 的 AUROC 为 0.4095，pair detection 为 0。这些结果促使我放弃简单地训练一个异常检测器，转而研究如何控制正常轨迹变化。

第二，我测试了一个轻量的 DeepLog-style sequence baseline，AUROC 为 0.5527，benign false alarm 为 28.13%，没有显示出实际增益。这里能下的结论只是“当前这个轻量实现没有帮助”，不能推广为所有序列模型都不适合这个问题。

第三，Delegation-transition 这条实验线最后被归档了。主要原因不是数据给出了明确反例，而是可恢复的决策边界太少，很多轨迹在边界后没有足够步骤可供分析，同时基础设施和 schema 也不够稳定。最终无法可靠回答 transition state 是否比静态检查提供更多信息。因此，这条路线是“当前设计无法验证”，不是“科学假设已被证明错误”。

第四，基于关键词的 refusal 分类器效果不好。在专门构造的 challenge set 上，它的 accuracy 为 42.5%，macro F1 为 0.384，并且容易把“找不到文件”之类的环境问题误判为拒绝。后续如果继续研究 resistance，需要人工标注和语境化判断，不能依赖关键词规则。

## 6. 跨模型实验为什么没有结果

我为 GPT-5 和 gpt-4.1 重新设计并冻结了一套 fresh-sealed 协议。前期 smoke test 和基础设施检查都通过了，正式收集时 GPT-5 完成了计划中的 80 条轨迹，但 gpt-4.1 因 API credit 耗尽只完成 68 条。

缺失并不是均匀分布的。最终 40 组任务中只有 33 组 control 和 treatment 都完整，而且 `transaction_preparation` 这个任务族的完整配对数变成了 0/5。虽然总样本数看起来还不算小，但完整缺少一个任务族会让 complete-case 分析产生明显的结构偏差。

因此我没有补造轨迹、没有用其他模型代替，也没有打开这批数据的科学结果。跨模型复制目前只能记录为“没有按原计划完成”。它既不能证明结果可以复现，也不能证明结果无法复现。

## 7. 其他行为信号的可测量性

我还检查了现有轨迹是否适合研究 refusal、adoption、task-scope expansion 和 recovery。

- **Refusal / resistance：**日志中的明显信号很少，关键词规则又没有通过验证。目前已经准备好 120 个真实 decision points 的人工标注包，但还没有完成两位独立标注者的标注，因此不能报告 resistance 结论。
- **Adoption acknowledgment：**同时保留暴露后文字和下一步动作的案例只有 2 个，数据太少。
- **Task-scope expansion：**没有轨迹同时保存足够明确的暴露前和暴露后任务表述，因此现有日志不适合分析。
- **Recovery：**40 组可行性样本中有 33 组可以判断，找到 1 个严格恢复候选和 6 个宽松恢复候选。这个方向具备进一步人工验证的价值，但现在还不能把候选数量当作 recovery rate，更不能把 recovery 等同于安全纠正。

## 8. 目前可以如何概括这个项目

我认为项目最合适的定位是：**以 benchmark 和测量方法为主，PIDR 表示方法为辅。**

目前比较扎实的贡献有三点：

1. 建立了一套配对、延迟暴露的 agent 轨迹测量协议；
2. 发现暴露后的行为分化显著超过暴露前基线，并观察到 Coding/Web 之间的差异；
3. 量化了大量正常的暴露前路径变化，说明 agent 监控必须区分随机执行变化和干预相关变化。

PIDR 可以作为第四点方法探索：它在表示层保留了更明显的干预相关分离，但实际检测价值还没有建立。

## 9. 接下来最值得做的事

如果继续推进，我认为优先级是：

1. 在资源允许时补齐 gpt-4.1 缺失轨迹，再按照已经冻结的协议完成真正的跨模型分析；
2. 完成两位独立人工标注者对 resistance 样本的标注，先验证测量工具是否可靠；
3. 人工检查 strict/relaxed recovery 定义，确认算法找到的“恢复”是否符合人的判断；
4. 如果继续方法研究，优先增加更强的序列 baseline 和真正跨 provider 的模型，而不是立即开发 PIDR-v2。

## 10. 结论边界

为了避免把结果说得过头，当前结论可以简单分成三类：

| 类型 | 内容 |
|---|---|
| 已有较强证据 | 暴露后轨迹分化增加；Coding/Web 幅度不同；正常轨迹存在大量自然分叉 |
| 有初步方法证据 | PIDR 保留更强的干预相关表示分离 |
| 目前不能判断 | PIDR 是否改善实际检测；结果能否跨模型复现；agent 是否表现出稳定 resistance；adoption 和 scope-expansion 效应 |

项目的详细数字、实验状态和证据文件仍保存在 `paper/CLAIM_EVIDENCE_MATRIX.csv`、`results/` 以及实验报告中。本报告只负责说明研究主线和目前真正能够支持的结论。
